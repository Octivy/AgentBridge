# AgentBridge 差距分析：客户端形态与产品化落地

日期：2026-08-13
触发：用户反馈——"中间连接器的客户端形态没看到，快速连接的方式没看到；虽然通过了部分软件
连接测试，但离真正落地产品还有差距。"

## 0. 一句话结论

**桥的技术管道已经够深，但"客户端产品"这一层几乎没有被真正建造。**
当前交付物本质上是"开发者验收装置"：它能证明链路通，却不能让一个新用户在产品里
完成"装客户端 → 连软件 → 给智能体下命令 → 拿交付物"的闭环。精力的投入方向
（管道与验收）与用户期待的方向（客户端体验与快速连接）错位了。

投入分布的硬数据：

| 层 | 代码量 | 说明 |
| --- | --- | --- |
| 后端管道（copilot_backend，不含 tests） | ~12,000 行 Python | 注册发现、MCP、票据、回滚、多模型、交付、Planner |
| 适配器（adapters/） | ~2,800 行 | Blender / SketchUp / Rhino |
| 全部客户端代码（client/ + desktop/） | ~867 行 C#/XAML | 两个壳，都只是后端托管 + 托盘 + 浏览器容器 |
| 真正的产品界面 | 1 个 725 行 ui.html | 工程控制台风格，桌面壳只是套在它外面的 WebView2 |

## 1. 按"理想用户旅程"逐步核对现状

产品愿景的用户旅程：**装客户端 → 快速连接软件 → 给智能体下命令 → 智能体操作软件 → 拿到交付物**。
逐步核对：

| 步骤 | 现状 | 差距 |
| --- | --- | --- |
| ① 安装客户端 | 便携包 = 源码拷贝 + PowerShell 脚本（setup-backend.ps1 / install-desktop.ps1）；依赖预装 Python 3.11+ 和 .NET 8 运行时；PRD 自己把 MSIX/Inno 列为"后续" | 不是用户产品，是开发包 |
| ② 首次打开 | 没有首次运行向导。打开即工程控制台 + 4 张离线软件卡片 | 用户不知道第一步该干什么 |
| ③ 配置"大脑"（模型） | 后端已有完整 `/admin/model-config` API（预设/测试/更新），**但 ui.html 没有设置页**；唯一途径是手编 `.env` | 新用户装完下不了第一条命令——这是闭环死穴 |
| ④ 连接软件 | Blender：点"一键安装"→ 手动打开 Blender → 适配器注册 → 还要 hostmcp 桥进程在跑（种子配置 `auto_start=false`，需手动点"启动"）。SketchUp/AutoCAD 类似或更手工（AutoCAD 要在 CAD 里加载插件 + 起 cadmcp + 对齐 token） | "一键安装"只覆盖了链路的第一小段；没有一个按钮完成"连接"全链路 |
| ⑤ 探测本机软件 | 无自动探测。面板不知道本机装了什么、什么版本；Blender 仅在安装时探测 %APPDATA% 版本目录 | 用户要对空气配置；连接失败只能去"连接监控"页自己排查 |
| ⑥ 接入 Agent | "一键写入 Codex 配置"存在且可用，需手动重启 Codex | 相对最好的一步，但无回读验证引导 |
| ⑦ 给智能体下命令 | 入口 A：overview 页角落 240px 高的小对话框（走 /chat/message，原为 AutoCAD copilot 设计）；入口 B：任务交付页的"运行 Agent 任务"表单（走 /agent/task） | 两个入口、两套语义并存；"智能体"在客户端里没有人格化的存在 |
| ⑧ 看过程 | `/agent/task` 同步阻塞（SERVICE_TIMEOUT=90s），UI 只显示"正在运行…"；无步骤流、无工具调用过程、无 dry-run 预览呈现 | 产品声称的核心安全机制（dry-run→票据）用户在界面上看不到 |
| ⑨ 确认写操作 | UI 可选"需要确认（annotate）"，但 host_task.py 里 annotate = 不传 confirm_write → 写操作被 blocked，任务返回 pending_write，**UI 没有确认/继续的交互落点** | 该模式在客户端实际上走不通 |
| ⑩ 拿交付物 | 交付列表是文本卡片（名称/类型/路径），无"打开文件/预览截图/一键回滚"动作 | 交付闭环只到"登记"，没到"交付" |

## 2. 为什么"看不到客户端形态"

1. **两个壳、零产品界面。** `client/`（230 行托盘程序）与 `desktop/`（WPF+WebView2 壳）
   功能重叠，都是"起 backend + 托盘 + 打开同一个 ui.html"；桌面端的左侧导航只是改
   `location.hash`。用户看到的所有界面都是那一个工程控制台 HTML。
2. **界面语言是工程语言。** host_id / host_kind / cwd / 启动参数逐行填、stdio 握手、
   注册表目录……这些是开发者概念，不是"设计/工程人员"的产品语言。
3. **智能体不是主角。** 一个以"人操作智能体"为模式的产品，客户端首屏是软件卡片列表，
   对话框缩在角落，模型配置藏在 .env。客户端没有呈现出"这里住着一个能帮你操作软件的智能体"。
4. **文档体系反衬。** docs/ 下 30+ 篇日期化文档、PRD 写到 v5、验收清单/交接模板/SOP 齐备——
   流程治理投入很大，而面向最终用户的安装向导、快速开始、界面文案、错误恢复指引几乎为零。
   这不是批评文档，而是说明开发重心一直在"证明自己做得对"，还没转向"让别人用得起来"。

## 3. 为什么"看不到快速连接"

逐软件的实际连接路径（每一步都需要人介入）：

- **Blender**（最好）：一键安装插件 → 手动打开 Blender → 自动注册 → （另需）hostmcp 进程在线
- **SketchUp**：一键安装扩展 → 手动重启 SketchUp（种子配置默认 `enabled=false`、launch 为空）
- **AutoCAD**：手动在 AutoCAD 加载插件 → 手动起 cadmcp → token 对齐 → 手动保持桥在线
- **Agent 侧**：一键写配置 → 手动重启 Codex

共性问题：

- **连接是多步手工链，不是一个动作。** "一键安装"按钮存在，但装完之后的剩余步骤
  全靠用户读 notes 文本自己完成。
- **无自动发现。** 面板不能主动告诉用户"检测到你装了 SketchUp 2025 和 Blender 5.1，
  点这里连接"。
- **状态不自愈。** 陈旧注册（软件已关但注册文件还在）、token 漂移、端口占用、桥崩溃，
  都需要人到"连接监控"页排查，没有自动清理/重连/修复建议。

## 4. 落地产品的关键缺口清单

P0（没有它们就没有第一个真实用户）：

1. **模型配置进 UI**：把已存在的 `/admin/model-config` API 接到面板"设置"页
   （选服务商→填 key→测试→保存），去掉 .env 依赖。
2. **统一"连接"动线**：每张软件卡片一个主按钮"连接"，内部编排
   检测安装 → 装适配器 → 拉起桥进程 → 等注册 → 健康检查 → 报告结果；
   失败给可执行的修复建议而不是一句"未发现已注册的宿主"。
3. **本机软件自动探测**：扫描注册表/常见安装路径，首屏直接呈现"可连接的软件"。
4. **首次运行向导**：检测软件 → 装适配器 → 配模型 → 写 Agent 配置 → 跑一个内置演示任务，
   让新用户 10 分钟内看到"智能体真的操作了软件"。

P1（客户端形态收口）：

5. **客户端双壳二选一**：建议保留 desktop/、废弃 client/，消除定位混乱。
6. **智能体为首屏**：对话/任务入口提到第一屏（流式步骤、工具调用、dry-run 预览、
   确认按钮），控制台功能退到二级页面；annotate 模式落地为真实交互。
7. **交付物可消费**：打开文件、预览截图、一键回滚成为卡片上的动作。

P2（分发与工程化）：

8. 真安装器（MSIX / Inno Setup）+ 自举或内嵌 Python 运行时，消灭"先装 Python 再跑脚本"。
9. 连接自愈：陈旧注册清理、端口冲突处理、桥崩溃自动重启的可见化。
10. 陌生环境实测：找没接触过项目的人从下载开始装一遍，记录每个卡点——
    这比再加任何自动化测试都更能暴露"落地差距"。

## 5. 路线建议

不建议继续沿"更多适配器 / 更多工具 / 更多验收"的方向投入。连接器门槛
（Blender/SketchUp/Rhino 实机 + AutoCAD 13 工具）已经足够证明管道可行。
下一个里程碑应该是**"陌生人 10 分钟闭环"**：只做 P0 四项 + P1 第 5、6 项，
把已有的管道能力包进一个真正的客户端体验里。这个里程碑通过的标准不是 pytest 数量，
而是一个没用过本项目的人能不看文档完成：安装 → 连接一个软件 → 配好模型 →
下一句话命令 → 看到智能体操作软件 → 拿到交付物。
